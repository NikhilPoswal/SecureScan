Technical Specification & Boundary Conditions

Engineering Notes & Limitations

A transparent breakdown of architectural constraints, network realities, anti-bot barriers, and design trade-offs discovered while developing SecureScan.

01
Design Principle

Passive, Read-Only Auditing Philosophy

SecureScan is strictly designed as a passive, non-intrusive security evaluation tool. It analyzes public cryptographic handshakes, HTTP response headers, SSL/TLS certificate chains, cookie attributes, DNS security records (SPF/DMARC), and public file status codes without altering state or injecting malicious payloads.

By deliberate design, SecureScan does not implement bot-detection evasion (e.g., residential proxy rotation, browser fingerprint spoofing, or headless automation designed to bypass security controls). Attempting to stealthily evade WAFs or mimic human behavior would contradict the tool's core premise: providing an authentic, reproducible audit of what standard external network clients observe.

02
Platform Reality

Cross-Project WAF & Shared Hosting Reputation

In modern serverless and cloud hosting ecosystems (such as Vercel, Cloudflare Pages, AWS Lambda, and Netlify), thousands of distinct web projects share common outbound egress IP ranges and incoming edge proxies.

During engineering trials, we observed that rapid, burst-heavy scanning of one Vercel-hosted domain can trigger edge WAF protection (HTTP 429 or 403 rate-limiting) that temporarily impacts subsequent scans of unrelated Vercel-hosted domains. Because edge mitigation rules often track request velocity per client IP against the entire shared edge infrastructure rather than a single customer tenant, multi-tenant platforms exhibit cross-project reputation coupling.

Key Takeaway: If you scan multiple sites hosted on the same infrastructure provider in rapid succession, edge rate limits may trigger even if each individual site has received only one request.

03
Edge Barriers

Cloudflare Turnstile & Managed Challenge Pages

Websites protected by advanced bot-mitigation services (such as Cloudflare Managed Challenges, Turnstile interstitials, Akamai Bot Manager, or AWS WAF Challenge) deliver dynamic JavaScript challenge barriers (e.g., <title>Just a moment...</title>) accompanied by HTTP 403/503 statuses and headers like cf-mitigated: challenge.

Because SecureScan operates as a high-performance Python HTTP client, it deliberately lacks a full JavaScript execution engine (such as V8 or Chromium). It cannot solve interactive cryptographic proof-of-work challenges, render Canvas fingerprints, or execute Turnstile tokens.

This is not a defect unique to SecureScan; it applies equally to standard command-line tools like curl, API clients, and automated vulnerability scanners. SecureScan includes dedicated challenge detection to identify these barriers honestly and inform users rather than computing an inaccurate security score.

04
Defensive Boundary

Server-Side Request Forgery (SSRF) Mitigations

Allowing an automated tool to fetch user-specified URLs introduces Server-Side Request Forgery (SSRF) vectors, where attackers could attempt to probe cloud instance metadata endpoints (e.g., 169.254.169.254), loopback adapters (127.0.0.1, ::1), or internal VPC addresses.

SecureScan applies strict defensive validation prior to creating outbound network sockets:

  • All submitted target hostnames are resolved to both IPv4 and IPv6 addresses before connecting.
  • Any destination falling within private, link-local, loopback, multicast, or reserved IP ranges is immediately rejected with a descriptive explanation.
  • HTTP redirects are validated at every hop to prevent open-redirect SSRF bypasses.
05
Infrastructure

Serverless Execution & Rate-Limiting Bounds

SecureScan runs entirely on stateless serverless compute instances. Memory is retained only for the lifespan of warm container invocations.

To protect shared resources from automated abuse, SecureScan implements a sliding-window rate limit (10 scans / minute per IP) enforced using client IP extraction from verified edge proxy headers. Scan history and previous results are stored exclusively in client-side sessionStorage, ensuring user privacy and zero persistent database tracking.

06
Audit Boundaries

Scope & Vulnerability Coverage (OWASP Mapping)

To maintain technical clarity and set honest expectations, it is essential to distinguish between a passive configuration auditor and an active vulnerability scanner.

SecureScan operates exclusively as a passive, read-only configuration tool. It inspects what a web server exposes through standard HTTP requests, TLS handshakes, and public DNS records. It deliberately does not perform active or dynamic testing—such as injecting SQL syntax, fuzzing parameters, or attempting cross-site scripting executions. Active vulnerability scanning is a fundamentally different, more invasive category of security testing (exemplified by tools like Burp Suite, OWASP ZAP, and sqlmap) and is intentionally outside this project's scope.

The table below defines how SecureScan's 10 passive checks map against common OWASP-style vulnerability classifications:

Category Coverage Why / Technical Distinction
XSS (Cross-Site Scripting) Indirect only We check whether a CSP defense exists, not whether the site actually has an exploitable XSS flaw. Confirming real XSS requires payload injection and observing execution, which this tool does not do.
SQL Injection (SQLi) Not covered Requires sending crafted input to parameters/forms and observing database-error behavior — active testing outside this tool's scope.
Security Misconfiguration Covered This is the tool's core strength: headers, CORS, cookies, dangerous HTTP methods, sensitive file exposure, and server fingerprinting are all checked directly.
Broken Access Control Not covered Requires testing authenticated flows (can user A reach user B's data, can a normal user reach admin routes). This tool has no concept of authentication/sessions to test against.
SSRF Different direction This tool protects ITSELF from being abused as an SSRF vector (blocks scanning internal/private addresses). It does not test whether the TARGET site is vulnerable to SSRF — that's the opposite check.
Outdated Components Indirect only Server fingerprinting can reveal a version banner, which could be manually cross-referenced against known CVEs, but this tool doesn't perform that lookup itself.
